# 两个面试题项目：从面试现场到可交付的工程系统

面试官留了两道题，我做了两个能真实跑起来的系统：一个抖音数据监控工具，一个推广申请处理 Agent。这轮把它们从"能跑"工程化到"能交付"——SQLite、并行、upsert、幂等、Docker、CI、评测，全部落地。

## 项目一：抖音数据监控工具

**解决什么问题**：运营要看一批抖音账号的涨粉、获赞、视频数据，人工一个个打开网页看太慢，还容易漏。

**系统形态**：Web 仪表盘 + 定时任务。

- 采集层：Playwright 带登录态访问，多账号并行（线程池上限 3 防风控），账号级失败自动重试
- 存储层：SQLite（WAL），scan_history / alerts 双表，从旧 JSON 真实迁移 419 条历史 + 143 条告警
- 集成层：飞书表格 upsert（video_id → 行号映射，脏数据正则过滤），告警推飞书群
- 工程化：启动自检、Docker、GitHub Actions CI，38 项单测

**核心链路**：定时触发 → 并行采集 → 增量计算 → 超阈值告警 → 飞书同步 → 仪表盘展示。

## 项目二：推广申请处理 Agent

**解决什么问题**：运营每天在群里发推广申请（抖加 / 垫付），人工录入多维表格易错、难对账。

**系统形态**：飞书群机器人，Master-Sub Agent 架构。

- 提取：规则正则优先 + LLM 兜底（口语化文本），字段名容错映射兼容模型输出漂移
- 校验：金额/笔数一致性、日期逻辑、抖加档位、笔误（编辑距离 ≤ 2）、重复申请，8 项规则
- 确认：模板确认卡片 + 修改意见闭环，入库前人工确认
- 幂等：MD5 指纹三态流转，重复消息不重复处理、不重复调 LLM
- 评测：基于真实确认记录双模式 P/R/F1 100%（见《准确率 100% 不是玄学》）

## 为什么面试题值得做成这样

面试题通常只要求"能跑"。往上走一步，它就从"作业"变成"作品"：

- **可验证**：38 + 26 项单测，改坏了立刻知道
- **可交付**：Docker 一键起，别人 clone 下来 5 分钟跑起来
- **可讲述**：每个设计都有理由——为什么 SQLite、为什么规则优先、为什么人工确认

> 面试可展开：把两道题工程化 = 展示的不只是"会写代码"，而是"知道一个真实系统要长什么样"。
