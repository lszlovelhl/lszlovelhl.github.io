# 单人全栈做帧间：两台服务器怎么分工

单人开发不代表只用一台机器。帧间有两类截然不同的算力需求，硬塞一台机器会互相拖垮，分开部署各自跑满。

## 两类负载的差异

| | 采源拆解机 | 生成服务机 |
|---|---|---|
| 任务 | 视频下载、抽帧、Whisper 转写、视觉特征提取 | LLM 拆解成稿、创作台推理 |
| 特点 | IO 密集 + 视觉特征计算 | 显存/推理密集 |
| 配置 | i7-12700KF + RTX 4070 12GB | A10 24GB + 64GB 内存 |

拆解管线要在 3~180 秒的视频里按 0.5~1 秒间隔截取关键帧（最多 180 张），跑转写、提特征——这活吃 CPU/IO 和显存带宽，但模型不大。生成服务跑的是大语言模型推理，瓶颈在显存容量和显存带宽。

## 为什么 LLM 放本地

帧间选择 Ollama 部署 Qwen 系列模型在本地生成机上跑，理由很实际：

1. **按次计费的产品，边际成本是命**。云端按 token 收费，用户拆一个视频就是几十上百次调用，量起来账单会吃掉毛利；本地推理只有电费
2. **数据不出服务器**。MCN 客户的内容资产留在自己的机器上，少了合规和信任的麻烦
3. **离线可用**。云端抽风/限流时本地模型兜底，链路不中断

## 云端也没有完全退出

纯本地会被模型能力天花板卡住：本地 8B/14B 模型的质量拼不过云端旗舰。所以架构是**本地兜底 + 云端提优**：

- 默认档位走免费/低价云端模型（glm-4-flash 等），成本可控
- 成稿这类质量敏感环节可以路由到本地 qwen3.5（慢但稳）
- 复杂任务按需切到云端 pro 档

选哪条路，由统一网关按"质量 × 成本 × 可用性"决定，业务代码无感知。

## 单人运维的取舍

双服务器意味着双份运维：监控、升级、备份。作为单人项目，我的原则是**能自动化的绝不手工**：定时任务、健康检查、一键部署脚本，都是为"一个人管两台机器"服务的。

> 面试追问点：你怎么决定一个推理任务走本地还是云端？——答档位路由 + 质量/成本契约，而不是写死在代码里。
